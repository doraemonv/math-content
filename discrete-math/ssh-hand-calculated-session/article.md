## 这一次，不说“然后通过密码学保证”

假设小林在笔记本上执行：

~~~bash
ssh alice@server.example
~~~

我们要跟踪一条命令 **ls**，从按下回车开始，一直看到服务器怎样还原出字母 l 和 s。中途不把关键步骤藏进“算法自动完成”这句话里。

但有一道教学上的难题：真实 SSH 使用 32 字节的曲线点、256 位哈希和复杂的认证加密。把真实数字全部写出来，只会得到几页十六进制字符，手算反而看不见结构。

所以本文分两层：

1. **手算层：** 使用很小的模数、教具版 RSA、异或和求和校验，把每一步算到具体整数；
2. **真实层：** 立即说明这一步在 OpenSSH 中对应 X25519、Ed25519、SHA-256 或认证加密的什么操作。

> **安全警告：** 本文的 \(p=23\)、教具版 RSA、单字节密钥、异或和求和标签全都极不安全，只能用来理解数据怎样流动，绝不能用于真实通信。它们保留的是协议的“骨架”，不是生产算法的安全强度。

读完后，你应该能回答：网络上到底发送了什么，什么从未发送，客户端和服务器各自算了什么，以及“核对成功”究竟核对的是哪个等式。

## 先看私钥和公钥文件的字符

小林真实使用 Ed25519 密钥时，本地文件的外观大致如下。

私钥文件 **~/.ssh/id_ed25519**：

~~~text
-----BEGIN OPENSSH PRIVATE KEY-----
这里是一段 Base64 字符；本文故意不展示任何真实私钥内容
-----END OPENSSH PRIVATE KEY-----
~~~

与它配对的公钥文件 **~/.ssh/id_ed25519.pub** 是一行：

~~~text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI…… laptop-example
~~~

这一行有三部分：

| 字符部分 | 含义 |
| --- | --- |
| ssh-ed25519 | 算法类型 |
| AAAAC3… | 二进制公钥结构的 Base64 文本编码 |
| laptop-example | 便于人辨认的注释，不参与密码学证明 |

Base64 只是把二进制写成可复制文本，**不是加密**。知道公钥的 Base64 字符，不等于知道私钥。RFC 8709 规定，SSH 的 Ed25519 公钥主体是 32 字节，签名是 64 字节，而且 Ed25519 用于签名，不用于加密终端流量。

公钥那一行可以放到服务器上 Alice 账户的 **authorized_keys** 中。私钥留在小林的电脑或受控的 SSH agent 中，正常认证时不会传到服务器。

还要再分清一对密钥：服务器自己有长期的**主机私钥和主机公钥**。客户端把可信的主机公钥或其指纹记在 **known_hosts** 中。于是这里至少有三类秘密：

| 秘密 | 谁持有 | 用完即丢吗 | 用途 |
| --- | --- | --- | --- |
| 服务器主机私钥 | 服务器 | 否 | 证明“我是这台服务器” |
| 用户私钥 | 客户端 | 否 | 证明“我是获准登录的用户” |
| 临时交换私数 | 双方各一个 | 通常是 | 为这次连接协商会话秘密 |

最容易混淆的一点是：长期私钥负责**签名身份证明**；真正持续加密终端数据的是本次连接派生出的**会话密钥**。

## 我们的手算实验材料

为了每一步都能用纸笔复核，规定下面的教具参数。

### 临时密钥交换

\[
p=23,\qquad g=5.
\]

客户端随机选择临时私数

\[
a=6,
\]

服务器随机选择临时私数

\[
b=15.
\]

### 服务器主机签名

我们用教具版 RSA 模拟“服务器对握手签名”。服务器选择：

\[
p_h=61,\qquad q_h=53,
\]

\[
n_h=p_hq_h=61\times53=3233,
\]

\[
\varphi(n_h)=(61-1)(53-1)=3120.
\]

取公开指数

\[
e_h=17.
\]

私有指数 \(d_h\) 必须满足

\[
e_hd_h\equiv1\pmod{3120}.
\]

这里选择

\[
d_h=2753,
\]

因为

\[
17\times2753=46801=15\times3120+1.
\]

所以服务器主机公钥是

\[
(n_h,e_h)=(3233,17),
\]

主机私钥的核心教具数字是

\[
d_h=2753.
\]

### 用户登录签名

再用另一套数字表示小林自己的用户密钥，避免把用户和服务器混成一人：

\[
p_u=47,\qquad q_u=59,
\]

\[
n_u=47\times59=2773,
\]

\[
\varphi(n_u)=46\times58=2668.
\]

仍取

\[
e_u=17,\qquad d_u=157,
\]

因为

\[
17\times157=2669=1\times2668+1.
\]

用户公钥是

\[
(n_u,e_u)=(2773,17),
\]

用户私钥的核心教具数字是

\[
d_u=157.
\]

真实 OpenSSH 的 Ed25519 密钥不是这两个 RSA 整数；这里故意选 RSA，只因为模幂可以完整手算。真实 Ed25519 的“公钥字符”是曲线点的编码，私钥文件还带有容器格式、校验和以及可选的口令保护。

## 第一幕：公开协商，但不发送临时私数

双方先公开 \(p=23\) 和 \(g=5\)。客户端计算公开交换值

\[
A=g^a\bmod p=5^6\bmod23.
\]

把指数拆成 \(6=4+2\)：

\[
5^2=25\equiv2\pmod{23},
\]

\[
5^4\equiv2^2=4\pmod{23},
\]

\[
5^6=5^4\cdot5^2\equiv4\cdot2=8\pmod{23}.
\]

所以客户端发送

\[
A=8,
\]

但不发送 \(a=6\)。

服务器计算

\[
B=g^b\bmod p=5^{15}\bmod23.
\]

因为 \(15=8+4+2+1\)，逐次平方：

\[
5^1\equiv5,\quad
5^2\equiv2,\quad
5^4\equiv4,\quad
5^8\equiv4^2=16\pmod{23}.
\]

于是

\[
5^{15}\equiv16\cdot4\cdot2\cdot5=640\equiv19\pmod{23}.
\]

所以服务器发送

\[
B=19,
\]

但不发送 \(b=15\)。

此时监听者能看到 \(23,5,8,19\)。在这个玩具世界中，他枚举几次就能找回 \(6\) 和 \(15\)，所以它没有真实安全性。真实的 X25519 使用巨大空间，使这种反推在已知方法下计算上不可行。

## 第二幕：双方独立算出同一个秘密

客户端收到 \(B=19\)，计算

\[
K_c=B^a\bmod p=19^6\bmod23.
\]

\[
19^2=361\equiv16\pmod{23},
\]

\[
19^4\equiv16^2=256\equiv3\pmod{23},
\]

\[
19^6\equiv19^4\cdot19^2\equiv3\cdot16=48\equiv2\pmod{23}.
\]

服务器收到 \(A=8\)，计算

\[
K_s=A^b\bmod p=8^{15}\bmod23.
\]

\[
8^2=64\equiv18,\qquad
8^4\equiv18^2=324\equiv2,
\]

\[
8^8\equiv2^2=4\pmod{23}.
\]

因为 \(15=8+4+2+1\)，

\[
8^{15}\equiv4\cdot2\cdot18\cdot8=1152\equiv2\pmod{23}.
\]

所以

\[
K_c=K_s=2.
\]

背后的总公式是

\[
K_c=(g^b)^a=g^{ab}\pmod p,
\]

\[
K_s=(g^a)^b=g^{ba}\pmod p.
\]

又因为 \(ab=ba\)，两边相等。注意：等式只解释双方为何相等；安全性还需要“从公开值反推私数很难”这一计算困难假设。

## 第三幕：服务器证明公开值不是中间人替换的

只算出 \(K=2\) 还不够。攻击者可以把 \(A\) 和 \(B\) 都换掉，分别与两端协商秘密。因此服务器要把此次握手绑定到自己的长期身份。

真实 SSH 会按规定编码并哈希这些内容：

\[
H=\operatorname{HASH}(V_C\|V_S\|I_C\|I_S\|K_S\|A\|B\|K).
\]

其中：

- \(V_C,V_S\) 是双方 SSH 版本字符串；
- \(I_C,I_S\) 是双方算法协商报文；
- \(K_S\) 是服务器主机公钥；
- \(A,B\) 是临时公开交换值；
- \(K\) 是共享秘密；
- \(\|\) 表示按协议编码后拼接，不是把十进制字符随便黏起来。

真实哈希会输出很多位。为了手算，假设这整段记录经过我们的教具哈希后得到

\[
H=65.
\]

这里的 65 只是预先给定的玩具输出，并不声称求和或取模能代替 SHA-256。

服务器用主机私有指数签名：

\[
S=H^{d_h}\bmod n_h=65^{2753}\bmod3233=588.
\]

怎样复算这个大指数？把

\[
2753=2^{11}+2^9+2^7+2^6+2^0
\]

并逐次平方取模，可得：

| 幂 | 余数 |
| --- | ---: |
| \(65^{1}\bmod3233\) | 65 |
| \(65^{2}\bmod3233\) | 992 |
| \(65^{4}\bmod3233\) | 1232 |
| \(65^{8}\bmod3233\) | 1547 |
| \(65^{16}\bmod3233\) | 789 |
| \(65^{32}\bmod3233\) | 1785 |
| \(65^{64}\bmod3233\) | 1720 |
| \(65^{128}\bmod3233\) | 205 |
| \(65^{256}\bmod3233\) | 3229 |
| \(65^{512}\bmod3233\) | 16 |
| \(65^{1024}\bmod3233\) | 256 |
| \(65^{2048}\bmod3233\) | 876 |

选择指数中出现的五行相乘再取模：

\[
65^{2753}\equiv
876\cdot16\cdot205\cdot1720\cdot65
\equiv588\pmod{3233}.
\]

服务器把以下信息发给客户端：

\[
\text{主机公钥 }(3233,17),\qquad B=19,\qquad S=588.
\]

它没有发送 \(d_h=2753\)。

客户端做两项完全不同的核对。

### 核对一：这把主机公钥是不是我信任的？

客户端把收到的主机公钥与 **known_hosts**、管理员预置公钥、SSH 证书或从可信渠道得到的指纹比较。签名算得再对，如果公钥本身属于攻击者，也只是证明“攻击者确实持有攻击者的私钥”。

### 核对二：签名是不是这把公钥产生的？

客户端用公开指数计算：

\[
S^{e_h}\bmod n_h=588^{17}\bmod3233.
\]

因为 \(17=16+1\)，逐次平方：

\[
588^2\equiv3046\pmod{3233},
\]

\[
588^4\equiv3046^2\equiv2639\pmod{3233},
\]

\[
588^8\equiv2639^2\equiv439\pmod{3233},
\]

\[
588^{16}\equiv439^2\equiv1974\pmod{3233}.
\]

因此

\[
588^{17}\equiv1974\cdot588\equiv65\pmod{3233}.
\]

它正好等于客户端自己计算的 \(H=65\)，所以玩具签名通过。

为什么能还原？因为 \(e_hd_h=1+15\varphi(n_h)\)。在满足 RSA 条件的消息上，欧拉定理给出

\[
H^{e_hd_h}
=H^{1+15\varphi(n_h)}
\equiv H\pmod{n_h}.
\]

真实 SSH 若协商 Ed25519，会使用椭圆曲线签名验证公式，而不是上述 RSA 等式；“私钥签名、公钥验证、签名绑定握手”这一逻辑位置相同。

## 第四幕：从共享秘密派生不同方向的钥匙

真实 RFC 4253 把 \(K\)、交换哈希 \(H\)、单字节标签和会话标识送入 HASH。加密密钥的两个方向分别使用字符 C 和 D，完整性密钥使用 E 和 F：

\[
K_{c\to s}=\operatorname{HASH}(K\|H\|\text{C}\|session\_id),
\]

\[
K_{s\to c}=\operatorname{HASH}(K\|H\|\text{D}\|session\_id).
\]

为了能继续手算，定义一个**不安全的教具派生函数**：

\[
F(K,H,L)=(K+H+\operatorname{ASCII}(L))\bmod256.
\]

代入 \(K=2,H=65\)：

\[
K_{c\to s}=F(2,65,\text{C})=(2+65+67)\bmod256=134,
\]

\[
K_{s\to c}=F(2,65,\text{D})=(2+65+68)\bmod256=135,
\]

\[
K_{\mathrm{mac},c\to s}=F(2,65,\text{E})=136,
\]

\[
K_{\mathrm{mac},s\to c}=F(2,65,\text{F})=137.
\]

标签不同，产生的钥匙用途不同。这就是密钥分离。双方交换 **SSH_MSG_NEWKEYS** 后，后续报文开始使用新算法和新密钥。

## 第五幕：服务器核对“小林确实有用户私钥”

到这里，客户端已经认出了服务器，但服务器还不知道客户端是谁。

服务器 Alice 账户的 **authorized_keys** 中预先登记了用户公钥

\[
(n_u,e_u)=(2773,17).
\]

用户认证签名不是对一句固定的“我是 Alice”签名；真实 SSH 会把首次交换哈希形成的 **session_id**、用户认证请求字段、公钥等内容绑定进去。这样，旧连接中抓到的签名不能简单搬到新连接重放。

假设本次应签数据经过教具哈希后是

\[
m=42.
\]

客户端用用户私有指数计算

\[
\sigma=m^{d_u}\bmod n_u=42^{157}\bmod2773=131.
\]

因为

\[
157=128+16+8+4+1,
\]

逐次平方的余数为：

| 幂 | 余数 |
| --- | ---: |
| \(42^1\bmod2773\) | 42 |
| \(42^2\bmod2773\) | 1764 |
| \(42^4\bmod2773\) | 390 |
| \(42^8\bmod2773\) | 2358 |
| \(42^{16}\bmod2773\) | 299 |
| \(42^{32}\bmod2773\) | 665 |
| \(42^{64}\bmod2773\) | 1318 |
| \(42^{128}\bmod2773\) | 1226 |

将 \(128,16,8,4,1\) 对应余数相乘并取模，得到

\[
\sigma\equiv1226\cdot299\cdot2358\cdot390\cdot42
\equiv131\pmod{2773}.
\]

客户端发送公钥标识和签名 \(\sigma=131\)，不发送 \(d_u=157\)。

服务器验证：

\[
\sigma^{e_u}\bmod n_u=131^{17}\bmod2773.
\]

\[
131^2\equiv523,\quad
131^4\equiv1775,\quad
131^8\equiv497,\quad
131^{16}\equiv212\pmod{2773}.
\]

所以

\[
131^{17}\equiv212\cdot131\equiv42\pmod{2773}.
\]

结果等于服务器自己算出的 \(m=42\)，而该公钥又确实在 Alice 的允许列表中，所以用户认证通过。

这一幕验证的是“客户端能够使用登记公钥对应的私钥”，不是“客户端把私钥交给服务器核对”。

## 第六幕：把命令 ls 变成线路上的数字

认证成功后，小林输入两个字符：

~~~text
ls
~~~

ASCII 编码为

\[
l=108,\qquad s=115.
\]

为了手算，教具加密规定每个字节与客户端到服务器密钥 \(134\) 做按位异或：

\[
C_1=108\oplus134=234,
\]

\[
C_2=115\oplus134=245.
\]

再用不安全的教具完整性标签：

\[
T=(C_1+C_2+K_{\mathrm{mac},c\to s})\bmod256.
\]

因此

\[
T=(234+245+136)\bmod256=615\bmod256=103.
\]

这时线路上的核心教具数据是：

\[
(234,245;\ 103).
\]

监听者不再直接看到 \(108,115\)，但必须再次强调：单字节异或密钥很容易破解，求和标签也很容易伪造。它们只让我们看清“密文”和“认证标签”是两项不同输出。

## 第七幕：服务器先核对，再还原

服务器收到 \((234,245;103)\)，先重算标签：

\[
T'=(234+245+136)\bmod256=103.
\]

因为 \(T'=T\)，教具包通过完整性检查。

然后使用同一个方向的加密密钥解密。异或满足

\[
(x\oplus k)\oplus k=x,
\]

所以

\[
234\oplus134=108,
\]

\[
245\oplus134=115.
\]

把 108 和 115 按 ASCII 解释，正好得到 **ls**。

假设攻击者把第一个密文字节从 234 改成 235，却没法生成正确标签，那么服务器算出

\[
(235+245+136)\bmod256=104\ne103,
\]

应拒绝这个包，而不是把篡改后的内容交给 shell。

真实 SSH 可能协商 ChaCha20-Poly1305、AES-GCM，或加密与 MAC 的其他受支持组合。真实认证标签依赖密钥、nonce、包序号和报文内容，不能用简单加法代替。现代 AEAD 的核心承诺是：只有认证成功的密文才交付为明文。

服务器的回复使用反方向密钥，避免两个方向共用同一把钥匙。若用教具密钥 \(135\) 加密 **OK**：

\[
O=79,\qquad K=75,
\]

\[
79\oplus135=200,\qquad75\oplus135=204.
\]

反方向教具标签为

\[
(200+204+137)\bmod256=29.
\]

客户端用反方向密钥核对 29，再将 200 和 204 解回 79 和 75。

## 一张完整的传输清单

| 顺序 | 方向 | 线路上能看到的教具内容 | 没有发送的秘密 | 接收方做什么 |
| ---: | --- | --- | --- | --- |
| 1 | 双向 | 版本与算法清单 | 无 | 选共同算法 |
| 2 | 客户端→服务器 | \(A=8\) | \(a=6\) | 服务器计算共享秘密 |
| 3 | 服务器→客户端 | \(B=19\)、主机公钥、\(S=588\) | \(b=15,d_h=2753\) | 客户端算 \(K,H\)，核对公钥和签名 |
| 4 | 双向 | NEWKEYS | \(K=2\) 及派生密钥 | 切换到加密通道 |
| 5 | 客户端→服务器 | 用户公钥标识、\(\sigma=131\) | \(d_u=157\) | 对照 authorized_keys 并验签 |
| 6 | 客户端→服务器 | 密文 \(234,245\) 与标签 103 | 明文 ls、会话密钥 | 先验标签，再解密执行 |
| 7 | 服务器→客户端 | 密文 \(200,204\) 与标签 29 | 明文 OK、反向密钥 | 先验标签，再解密显示 |

监听者当然仍能看到 IP、端口、连接时刻、包长度和大致流量节奏。SSH 保护内容，不会让网络连接隐形。

## 手算模型与真实 OpenSSH 一一对应

| 手算模型 | 真实 SSH 中的对应物 | 哪一点不能照搬 |
| --- | --- | --- |
| \(5^a\bmod23\) | 常见协商结果之一是 X25519 临时密钥交换 | 真实曲线运算不是模 23 的普通幂 |
| 教具 RSA 主机签名 | 协商的主机签名，例如 Ed25519 | Ed25519 不是教材 RSA |
| \(H=65\) | 对严格编码的握手记录做 SHA-256 等规定哈希 | 真实哈希不是把字段简单相加 |
| \(F(K,H,L)\) | RFC 规定的 HASH 密钥派生 | 真实输出是高熵多字节材料 |
| 单字节异或 | ChaCha20 或 AES 等对称加密构造 | 重复单字节异或不安全 |
| 求和标签 | Poly1305、GCM 标签或 MAC | 求和标签可以轻易伪造 |
| 教具 RSA 用户签名 | Ed25519、RSA-SHA2 等用户签名 | 算法与编码必须按协商规范 |

协议中的算法不是凭文章标题固定的。实际连接选择什么，要看客户端、服务器配置和协商结果。可在不泄露敏感日志的前提下使用：

~~~bash
ssh -vv alice@server.example
~~~

查看调试输出中的 key exchange、host key、cipher 等字段。

## 为什么攻击者不能把整套过程原样重放？

答案不是“因为有一个签名”，而是因为签名绑定了本次连接。

服务器主机签名绑定双方版本、算法协商、主机公钥、两边临时交换值和共享秘密。改动其中一项，客户端重算的交换哈希就不同。

用户认证签名又包含首次交换得到的会话标识以及本次认证请求。攻击者从旧连接复制一份用户签名，放入临时交换值不同的新连接，待签消息已经改变，验证不会通过。

数据包完整性还结合方向、密钥以及真实协议中的包序号或 nonce。复制、调序或篡改包不会自然得到一个仍有效的新标签。

这就是“把上下文签进去”的价值：签名不是一张永远可复印的身份证照片，而是对“这把身份钥匙正在参与这一场具体会话”的证明。

## 第一次连接为什么仍然需要你核对指纹？

设中间人自己生成一对主机密钥。他完全可以对自己制造的握手正确签名。数学验签会说：“收到的公钥与签名相配。”但数学不知道这把公钥是不是你原本要找的服务器。

所以客户端还必须回答一个来自系统外部的问题：

\[
\text{收到的主机公钥}
\stackrel{?}{=}
\text{可信渠道认定的服务器主机公钥}.
\]

首次连接若无条件接受陌生指纹，只建立了“以后别悄悄换钥匙”的记忆，没有证明第一次见到的就是正确服务器。后续出现主机指纹变化，也不能只为消除警告而删除旧记录；应先从云控制台、管理员或其他可信渠道查清变化原因。

## 常见误解

### “公钥是一串乱码，所以公钥也是秘密”

不是。公钥本来就可以公开。Base64 只负责文本编码，数学困难在于不能从公钥有效反推出私钥。

### “服务器用我的公钥把命令加密”

通常不是。用户公钥用于验证登录签名；终端流量由临时密钥交换派生的会话密钥加密。

### “签名就是用私钥加密全文”

这种说法对现代签名并不准确。真实 Ed25519 有自己的签名方程和编码规则。本文使用教具 RSA 模幂，只是为了把“私钥产生证明、公钥核验证明”手算出来。

### “客户端算出共享秘密，就知道对面一定是服务器”

不是。裸密钥交换只得到“与网络另一端共享的秘密”。主机签名和可信主机公钥才把另一端绑定到服务器身份。

### “私钥设了口令，口令会发给服务器”

通常不会。口令用于在本地解锁私钥容器；服务器收到的是签名证明。若客户端本身被恶意软件控制，解锁后的密钥使用仍可能被滥用。

### “数学等式都成立，所以服务器不可能被攻破”

不成立。漏洞、弱配置、私钥泄露、恶意客户端、供应链问题和已失守端点都不在这些等式的保证范围内。

## 你可以亲自复算的最小脚本

手算完成后，可以用 Python 的三参数 pow 复核模幂。它计算的是“先乘方再取模”的高效版本，不会真的构造巨大整数。

~~~python
print(pow(5, 6, 23))       # 8
print(pow(5, 15, 23))      # 19
print(pow(19, 6, 23))      # 2
print(pow(8, 15, 23))      # 2

print(pow(65, 2753, 3233)) # 588
print(pow(588, 17, 3233))  # 65

print(pow(42, 157, 2773))  # 131
print(pow(131, 17, 2773))  # 42

print(108 ^ 134, 115 ^ 134)  # 234 245
print(234 ^ 134, 245 ^ 134)  # 108 115
~~~

这个脚本只验证本文算术没有抄错，不证明玩具算法安全，也不等于实现了 SSH。

## 练习答案

### 题 1

五个核心秘密是客户端临时私数 \(a=6\)、服务器临时私数 \(b=15\)、服务器主机私有指数 \(d_h=2753\)、用户私有指数 \(d_u=157\) 和双方各自算出的共享秘密 \(K=2\)。由 \(K,H\) 派生出的 134、135、136、137 也不能发送给监听者。

### 题 2

\[
A=5^7\bmod23=(5^6\bmod23)\cdot5=8\cdot5=40\equiv17.
\]

客户端算：

\[
K=19^7\bmod23=(19^6\bmod23)\cdot19=2\cdot19=38\equiv15.
\]

服务器也会得到

\[
17^{15}\bmod23=15.
\]

### 题 3

签名正确只证明签名者持有“当前收到的公钥”对应的私钥。若不核对公钥身份，中间人可发送自己的公钥并用自己的私钥产生正确签名。两项都通过，才能把一次正确签名绑定到预期服务器。

### 题 4

\[
17\times157=2669=2668+1,
\]

所以余数是 1。它使公有指数和私有指数在模 \(\varphi(n_u)\) 意义下互逆，从而让教具签名经公开指数运算后回到原消息。

### 题 5

客户端会把收到的新 \(B\) 放入自己的交换哈希，得到不同的 \(H'\)。攻击者没有服务器主机私钥，不能为 \(H'\) 生成正确主机签名；继续转发服务器对旧 \(H\) 的签名会验证失败。

### 题 6

\[
65\oplus134=199,
\]

\[
199\oplus134=65.
\]

因此解密回 ASCII 65，也就是 A。

### 题 7

它缺少抗伪造性。公开的简单求和让攻击者不需要 MAC 密钥也能调整标签。真实 MAC 或 AEAD 标签以秘密密钥为输入，使攻击者即使知道算法和密文，也难以为修改后的报文生成有效标签。

### 题 8

会话密钥持续加密命令和输出；服务器主机私钥证明服务器身份；用户私钥证明登录者拥有获准使用的用户凭证。

## 如果你真的理解了

试着不用“SSH 很安全”这句笼统的话，独立回答：

1. 为什么线路上出现公钥和签名不会泄露私钥？
2. 为什么同一个连接同时需要主机签名与用户签名？
3. 为什么共享秘密相等的代数证明，不等于共享秘密安全的证明？
4. 为什么首次主机指纹的可信来源是密码学公式之外的一环？
5. 如果客户端已经被木马控制，本文哪几层保护仍然无法阻止命令泄露？

如果你能沿着“临时交换值 → 共享秘密 → 主机签名 → 会话密钥 → 用户签名 → 密文与标签”的顺序，说明每一个值由谁产生、谁能看到、用于验证什么，那么这条 SSH 通道就不再是一个黑盒。
